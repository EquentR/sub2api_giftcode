# 订阅重置次数赠送上线手册

本次迁移停用旧的历史订阅自动补发，保留已经授予的基础周期次数，并新增独立的活动赠送账本。迁移本身不会创建任何营销赠送批次，也不会调用上游重置接口。

## 上线前

1. 确认当前应用版本、数据库绝对路径和可用磁盘空间。
2. 停止所有会写入该 SQLite 数据库的应用实例和后台 worker。
3. 对数据库文件及其 `-wal`、`-shm` 文件做同一时点备份；推荐先执行 SQLite 在线备份或 `VACUUM INTO`，不要只复制正在写入的主文件。
4. 在旧版本数据库上执行只读预检：

   ```powershell
   sqlite3 <数据库绝对路径> ".read docs/operations/subscription-reset-bonus-preflight.sql"
   ```

5. 保存完整输出。`quick_check` 应为 `ok`，`foreign_key_check` 应无行；重复阻塞操作允许迁移程序按保守策略处理，但必须记录其订阅 ID。

## 启动迁移

1. 部署新二进制和前端静态文件，但暂不创建赠送批次。
2. 只启动一个后端实例。数据库迁移在服务启动时幂等执行：
   - 增加赠送批次、明细、权益和延期事件表；
   - 将旧 `pending/running/failed` 补发任务标记为 `superseded`；
   - 仅忽略旧补发触发时间之前、尚未授予且次数为零的历史周期；
   - 已有正数周期不回收；重复的阻塞操作按“已消耗”保守收敛，不会释放后再次调用上游。
3. 等待后端健康检查通过后再恢复其他实例。

## 迁移后核验

执行只读后检：

```powershell
sqlite3 <数据库绝对路径> ".read docs/operations/subscription-reset-bonus-postflight.sql"
```

核验要求：

- `quick_check` 为 `ok`，`foreign_key_check` 无行；
- 四张新表全部列出；
- 名称以失败语义表达的六项检查结果全部为 `0`；
- 旧补发任务不再出现 `pending/running/failed`；
- `marketing_batches_created_by_migration` 必须为 `0`。

随后检查管理端：

1. “档位设置”不再显示历史自动补发任务。
2. “重置次数赠送”可选择一个或多个有限额订阅分组，并能先预览、后创建。
3. 创建一个内部测试用户的定向小批次，确认批次明细只绑定预览中的有效订阅。
4. 用户订阅卡片应分别显示基础次数、活动赠送、合计和下一消耗来源。
5. 对旧失败任务保持观察，确认它们不会再次进入运行态。

## 线上缺失权益处置

先根据业务记录确认用户和订阅分组，再通过独立“重置次数赠送”页面创建定向批次。不得直接修改 `reset_used`、`reset_limit` 或 attempt 状态；如有多个分组，按实际缺失范围多选。预览中的订阅数、分组分布和缺失用户必须由两人复核后才能确认。

## 回滚边界

新版本一旦产生赠送批次、重置 attempt 或延期事件，不支持把数据库原地降级给旧版本继续写入。若迁移后尚未开放写流量且核验失败，可停服并恢复整套迁移前备份；若已经产生新账本数据，应保留数据库并修复程序，不得用旧备份覆盖线上新增操作。
