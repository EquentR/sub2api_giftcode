# 辅助调度器模型集合通道规范

## 问题陈述

辅助调度器目前将账户同时作为健康评估和故障转移的基本单位。如果任一主账户出现临时的账户级或模型级问题，调度器会一次性启用所有备用账户。对于可提供多个模型的账户，以及成本各异的备用账户，这种行为粒度过粗。

Sub2API 的优先级机制无法提供所需的成本保护，因为即使较高优先级的账户仍然可用，较低优先级的账户也可能被选中。维护 Sub2API 分支同样不在范围内，因为这会使上游升级成本高昂。因此，调度器必须保持外置，并仅使用现有的账户级 `schedulable` 开关作为路由控制手段。

调度器需要针对已配置的模型集合评估可用性，按照成本通道逐级增加备用容量，在较高成本通道开启时保留较低成本容量，并在较低成本通道恢复后移除较高成本容量。当上游状态未知或写入结果无法验证时，调度器必须避免开启高成本通道。

## 解决方案

将每条主账户/备用账户规则替换为模型集合通道规则。每条规则包含一个非空模型集合，以及至少两个按成本从低到高排列的账户通道。已启用通道始终构成从通道 1 开始的连续前缀。

调度器对已开启前缀内健康模型覆盖范围的并集进行评估。仅当每个已配置模型在该前缀内至少有一个当前可用账户时，覆盖才算完整。如果在应用相应的确认策略后覆盖仍不完整，调度器将仅开启下一个通道，但不得超过规则的自动通道上限。成本更低的通道保持开启。

当成本更低的前缀重新获得完整覆盖，并在恢复期内保持稳定时，调度器将关闭所有成本更高的通道，仅保留能够提供完整覆盖的最低成本前缀。Sub2API 可以将符合条件的流量路由到已开启前缀中的任意账户；累积开启可以提高可用性，但无法在已开启通道之间实现严格的成本隔离。

所有上游开关操作均采用期望状态协调机制。写入后必须执行权威读取。未知观测结果和不确定写入在解决前会阻止进一步升级。已启用规则对其账户拥有排他所有权，防止多条规则对账户级开关发出相互冲突的操作。

## 用户故事

1. 作为管理员，我希望在调度规则上配置一组模型，以便故障转移决策能够反映该规则需要保护的模型。
2. 作为管理员，我希望按照成本从低到高排列账户通道，以便逐步引入备用容量。
3. 作为管理员，我希望每个通道能够包含多个账户，以便 Sub2API 可以在可用容量内均衡流量。
4. 作为管理员，我希望通道 1 表示基准账户池，以便直接替代现有的主账户设计意图。
5. 作为管理员，我希望已启用通道构成连续前缀，以便开启较高成本通道时始终保留成本更低的通道。
6. 作为管理员，我希望基于所有已开启通道计算模型覆盖，以便能力互补的账户可以共同满足模型集合的需求。
7. 作为管理员，我希望每个已配置模型都至少保留一个可用账户，以便任一模型未被覆盖时能够触发组级故障转移。
8. 作为管理员，我希望账户整体故障会使该账户不再为任何已配置模型提供覆盖，以便自然地处理整账户故障。
9. 作为管理员，我希望特定模型的冷却仅使对应的账户与模型组合失去覆盖资格，以便准确保留对其他无关模型的覆盖。
10. 作为管理员，我希望已确认的账户整体故障可以立即触发升级，以便快速应对确定性的账户故障。
11. 作为管理员，我希望临时模型故障需要连续观测两次后才触发升级，以便瞬态状态不会立即增加成本。
12. 作为管理员，我希望每次确认决策最多只开启一个额外通道，以便调度器不会在一次执行中跨越多个成本层级。
13. 作为管理员，我希望升级后成本更低的通道保持开启，以便已经恢复或部分可用的低成本容量继续承载流量。
14. 作为管理员，我希望恢复时选择能够提供完整模型覆盖的最低成本前缀，以便移除不必要的高成本容量。
15. 作为管理员，我希望低成本覆盖在收缩前保持稳定约两分钟，以便恢复状态不会引发快速反复切换。
16. 作为管理员，我希望关闭已恢复前缀之上的所有通道，以便成本回落到当前足以满足需求的最低水平。
17. 作为管理员，我希望能够配置可自动开启的最高通道，以便高价容量仍受明确控制。
18. 作为管理员，我希望超过自动上限时产生可见警告且不打开被禁止的通道，以便服务压力不会悄然绕过成本策略。
19. 作为管理员，我希望未知或格式异常的上游状态能够阻止升级，以便管理平面故障不会授权额外支出。
20. 作为管理员，我希望上游读取失败时保留最近一次已验证的期望状态，以便调度器不会执行推测性的路由变更。
21. 作为管理员，我希望每次写入 `schedulable` 后都进行回读和验证，以便不会仅凭成功的 HTTP 响应就认定操作已经生效。
22. 作为管理员，我希望超时的写入进入不确定状态，以便调度器考虑上游变更可能已成功的情况。
23. 作为管理员，我希望在进一步升级前重试并协调不确定状态，以便不会累积相互重叠且尚未解决的变更。
24. 作为管理员，我希望部分写入能够向已持久化的期望状态收敛，以便进程中断不会永久破坏通道状态。
25. 作为管理员，我希望已启用规则对其账户拥有排他所有权，以便两条调度规则不会以相反方向切换同一账户。
26. 作为管理员，我希望已禁用规则不保留账户所有权，以便非活动配置不会妨碍账户复用。
27. 作为管理员，我希望拒绝同一规则内账户重复归属，以便通道所有权和覆盖关系保持明确。
28. 作为管理员，我希望能够检测、纠正并报告对规则所拥有账户的上游手动变更，以便实际路由恢复到已配置策略。
29. 作为管理员，我希望规则列表显示当前开启至哪个通道以及转换状态，以便了解当前的成本敞口。
30. 作为管理员，我希望规则列表显示缺失的模型覆盖及升级原因，以便诊断通道为何开启。
31. 作为管理员，我希望未验证、已阻塞和达到自动上限的状态能够明确区分，以便运维不确定性不会被呈现为健康运行状态。
32. 作为管理员，我希望手动检查与周期性调度器执行相同的协调流程，以便手动行为与自动行为不会出现偏差。
33. 作为管理员，我希望规则编辑根据当前上游数据验证模型名称和账户能力，以便拒绝明显不可用的配置。
34. 作为管理员，我希望账户信息补充失败仍然可见，同时不隐藏已持久化的规则，以便临时上游中断不会导致配置从界面消失。
35. 作为管理员，我希望禁用或删除规则时，在释放控制权前关闭由调度器开启的备用通道，以便高成本账户不会意外保持开放。
36. 作为管理员，我希望规则禁用时基准通道账户保持 `schedulable`，以便禁用自动化不会移除正常服务池。
37. 作为管理员，我希望更新规则时，在释放已移除的备用通道账户前验证这些账户已经关闭，以便旧成员关系不会遗留成本敞口。
38. 作为管理员，我希望旧版主账户/备用账户规则必须经过显式模型集合配置，以便升级过程不会猜测具有重大成本影响的行为。
39. 作为管理员，我希望旧版规则在等待迁移期间保留其上游状态，以便部署不会悄然中断服务或改变成本敞口。
40. 作为管理员，我希望界面说明累积开启通道不等同于严格成本隔离，以便理解 Sub2API 仍然存在的路由行为。

## 实施决策

- 此功能完全保留在外部调度器中。不需要修改 Sub2API 源码、自定义优先级语义或维护上游调度器分支。
- 唯一的路由变更手段是 Sub2API 的账户级 `schedulable` 开关。`model_rate_limits` 仅作为健康数据进行观测，不会被写入作为调度策略。
- 一条规则包含名称、启用状态、非空模型集合、至少两个有序通道，以及规则级 `maximum_auto_lane`。面向管理员的通道编号从 1 开始。
- 通道 1 是基准池。当规则已启用并正常运行时，期望的开启状态是从通道 1 到 `open_through_lane` 的连续前缀。
- 通道开启采用累积方式。当成本更高的通道开启时，成本更低通道中的账户仍保持期望的 `schedulable` 状态。
- 覆盖范围基于已开启前缀中所有账户的并集进行评估。当该并集能为每个已配置模型提供至少一个可用账户时，覆盖即为完整。不同账户可以分别覆盖不同模型。
- 账户级整体不可用会使该账户不再为任何模型提供覆盖。模型级不可用仅移除受影响的账户与模型组合。
- 类型化可用性观测将区分 `usable`、`unavailable` 和 `unknown`。观测会考虑账户状态、账户级临时调度时间窗口、目标模型的限流时间窗口、支持的模型与模型映射，以及观测数据的新鲜度。格式异常或不完整的数据应判定为 `unknown`，而不是 `unavailable`。
- 可用性适配器将向调度器公开带模型限定的观测结果，不要求协调逻辑直接解析无类型的上游账户扩展数据。
- 规则使用面向 Sub2API 请求的模型名称。在匹配模型级冷却数据前，配置验证和观测必须根据每个账户支持的模型及其映射，以一致方式解析这些名称。
- 确定性的账户整体故障可以立即确认升级。临时模型级不可用需要连续两次协调观测。未知观测绝不能作为授权升级的证据。
- 已确认的覆盖缺口最多开启下一个通道。如果该通道超过 `maximum_auto_lane`，则不打开任何账户，并使规则进入可见的“受自动上限阻塞”状态。
- 恢复过程计算当前能够提供完整模型覆盖的最低成本通道前缀。只有同一前缀持续保持完整覆盖约两分钟后，才执行收缩。恢复候选前缀发生变化时，稳定期重新计时。
- 收缩时从成本最高的通道开始向下关闭，直至达到目标前缀。整个收缩过程中，成本更低的通道保持开启。
- 规则状态将持久化以下信息：期望开启至哪个通道、已观测/已验证的通道状态、目标通道、转换代次与状态、升级证据、恢复候选及其起始时间、最后观测时间、最后验证时间，以及可操作的错误或警告信息。
- 转换状态必须区分稳定、应用中、不确定、失败和阻塞结果。具体存储字段可以遵循仓库约定，但必须保留这些面向外部可见的区别。
- 协调采用基于期望状态的幂等机制。每次执行都会将持久化意图与权威上游账户状态进行比较并修复偏差，而不是仅依赖上一次转换响应。
- 每次上游变更后都必须读取账户，并验证最终的 `schedulable` 值。响应数据缺失、账户身份不匹配、超时或回读失败均不算验证成功。
- 不确定的开启操作视为账户可能已开启。不确定的关闭操作视为账户可能仍处于开启状态。只要规则存在任何尚不确定的变更，就不得开启其他通道。
- 已启用规则对其所有通道中的每个账户拥有排他所有权。已禁用规则释放所有权。所有权验证适用于所有通道位置，并通过持久化存储以事务方式强制执行，而不是仅依赖进程内检查。
- 对已启用规则所拥有账户进行的手动变更属于状态偏差。下一次协调会恢复配置的期望值，并记录对管理员可见的警告。
- 禁用或删除规则时，必须先关闭并验证通道 1 以上的所有通道，再释放所有权。通道 1 保持 `schedulable`，以确保不会仅因禁用自动化而移除正常服务。
- 更新已启用规则时，必须安全协调已移除或重新排序的成员关系。基准通道以上被移除的账户必须先关闭并完成验证，之后才能释放所有权。无法建立安全结果的更新必须保持未应用状态，或明确显示为不确定状态。
- 管理界面保留列表、创建、编辑、删除、启用/禁用、刷新和手动检查工作流。其契约从主账户/备用账户数组演进为模型集合和有序通道，响应中应公开足够的运行时状态，以解释已开启前缀和转换过程。
- 管理界面提供有序通道编辑器、模型多选、自动通道上限控制、当前 `open_through_lane`、覆盖缺口、恢复进度、转换不确定性和上游错误。
- 旧版规则会在结构上将主账户和备用账户数组分别转换为通道 1 和通道 2，但不会推断模型集合。旧版规则进入“需要迁移”状态，在管理员选择模型并保存有效规则前，不执行新的上游写入。
- 迁移不会悄然改变旧版账户的上游 `schedulable` 状态。界面必须公开迁移要求和实际观测到的账户状态，以便管理员有意识地处理现有成本敞口。
- 调度器继续周期性运行并支持手动协调。所有协调入口共享同一条行为路径。
- 在单应用实例中，可以继续使用现有的进程内串行化机制，但持久化所有权和期望状态必须防止出现无提示的配置冲突。本规范不引入多副本分布式协调。

## 测试决策

- 主要测试边界是应用层调度器接口，其后端使用真实的内存数据库和伪造的 Sub2API HTTP 服务器。测试断言持久化的规则/运行时行为以及对外发出的账户开关请求，而不是私有辅助函数调用。
- 调度器行为测试将覆盖：并集覆盖完整与不完整、账户与模型能力互补的覆盖、账户整体故障、单模型冷却、连续两次观测后升级、确定性故障立即升级、每次仅升级一个通道，以及自动通道上限。
- 恢复测试将覆盖：选择成本最低且足够的前缀、稳定期计时、恢复候选变化、从高成本到低成本的关闭顺序，以及恢复状态反复波动后的还原行为。
- 协调测试将覆盖：成功写入并回读、响应成功但数据缺失、上游提交后超时、回读不匹配、部分账户变更、根据持久化期望状态模拟进程重启，以及不确定结果之后的状态收敛。
- 所有权测试将覆盖：规则内重复账户、已启用规则之间的冲突、已禁用规则释放后的复用、事务性更新冲突、成员关系移除，以及上游手动状态偏差。
- 生命周期测试将覆盖禁用、删除和更新行为，包括经验证地关闭非基准通道，以及保留基准服务。
- 可用性适配器契约测试将断言准确的上游请求，以及对以下信息的类型化解释：账户状态、支持的模型、模型映射、账户级时间窗口、模型级冷却、格式异常的扩展数据、已过期时间戳和不可用的管理端点。
- HTTP 行为测试将通过完整路由和真实存储调用已认证的管理路由，检查授权、验证、响应封装、运行时状态公开、需要迁移的规则，以及上游错误传播。
- 前端契约测试将覆盖有序通道和模型集合的序列化，以及以下状态的渲染规则：已开启前缀、阻塞状态、不确定转换、迁移要求和累积开启的成本说明。除非通道编辑器需要更完整的组件测试，否则测试应遵循仓库既有的轻量前端测试风格。
- 迁移测试将从旧版模式开始，验证确定性的双通道转换、不推断模型、需要迁移的行为、不自动执行上游变更，以及保留现有规则标识和审计数据。
- 测试使用可控时钟验证连续观测和恢复稳定期行为，不得依赖真实休眠或调度器时钟周期。
- 良好测试应断言管理员可见的策略结果和上游开关效果，不应固化内部辅助函数名称、JSON 存储布局或协调实现的特定拆分方式。

## 范围之外

- 修改或派生 Sub2API 的调度行为。
- 将 Sub2API 优先级视为严格的后备顺序。
- 将调度器所有权写入 `model_rate_limits`，或在上游增加模型级硬开关。
- 在累积开启的通道之间实现严格成本隔离。
- 阻止在账户开关改变后，已排队、正在处理、具有粘性，以及 WebSocket、Live 或 Realtime 请求继续使用该账户。
- 将一个物理凭据拆分为特定于模型的逻辑 Sub2API 账户。
- 在一条规则内为不同模型子集维护独立通道状态。
- 以美元计价的预算、计费截止机制或支出预测。
- 自动开启 `maximum_auto_lane` 以上的通道。
- 分布式领导者选举或多副本调度器租约。
- 自动推断旧版规则的模型集合。

## 补充说明

- 本设计有意通过升级后保留成本更低的通道来优先保障服务连续性。当较高成本通道开启时，Sub2API 可能会将本来仍有低成本容量的模型路由到成本更高的账户。调度器会限制这种成本敞口的持续时间和深度，但不会彻底消除它。
- 已禁用或需要迁移的规则不得被描述为正在主动执行。界面应将观测到的上游账户状态与调度器期望状态分开显示。
- 模型集合覆盖是一种健康判断，并不能证明剩余额度或未来请求一定成功。由于意外升级会直接产生财务后果，未知观测应按保守方式处理。
- 初始约定的默认值是：临时模型不可用需连续观测两次后升级，收缩前需保持约两分钟的低成本完整覆盖。这些值可以在首个版本中以常量表示；本规范不要求管理员可配置这些值。
