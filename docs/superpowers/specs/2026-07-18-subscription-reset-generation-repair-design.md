# 订阅重置周期代际绑定与补偿修复设计

## 背景

订阅额度重置功能上线后，旧数据补发在生产环境暴露出两个相互关联的问题：

1. 周期对账仅按 `upstream_user_id + sub2api_group_id` 聚合全部本地周期，再统一绑定到当前有效的上游订阅。用户在同一分组中存在多个上游订阅代际时，已撤销的旧订阅会与当前有效订阅混在同一个推断区块中。
2. 批量补偿直接延长上游订阅到期时间，但本地没有保存延期前后边界，也没有同步延长对应的重置周期。后续只能从当前总到期时间反推，无法区分购买有效期、补偿天数和其他外部延期。

生产环境中的确定性证据如下：

- Std 档位补发任务共有 4 条历史周期，仅处理 2 条并授予 2 条，另外 2 条持续报 `historical periods await authoritative reconciliation`。
- 用户 1 的申请 14 与上游订阅 18 的开始时间一致，但订阅 18 已撤销。
- 用户 1 的申请 22 与当前有效上游订阅 21 的开始时间一致，但用户卡片被判定为 `external_period`，未获得 3 次重置机会。
- 用户 5、6 的 Std 订阅分别参加过 `+3 天` 和 `+1 天`批量补偿；上游订阅跨度大于本地档位的 30 天有效期。
- Pro 档位的两条历史交付对应的上游订阅均已撤销，因此零授予是正确结果。

当前算法会把用户 1 的两个 30 天周期作为一个 60 天区块，从当前仅 30 天的订阅 21 到期时间向前反推，结果早于订阅 21 的开始时间，触发重叠保护并阻塞整个分组。这使应当判定为不授予的旧周期和应当授予的当前周期同时无法完成。

## 目标

- 将每个本地重置周期绑定到明确的上游 `subscription_id`，不同订阅代际独立对账。
- 将批量补偿建模为可持久化、可审计、可恢复的延期事件。
- 补偿天数延长当前本地重置周期的结束时间，但不增加重置次数。
- 已撤销或已过期的历史订阅周期标记为已处理但不授予次数。
- 无法唯一匹配的历史周期进入管理员待处理列表，不阻塞同组其他周期。
- 通过版本化、可 dry-run、幂等的修复任务纠正现有生产数据，避免直接手工修改数据库。

## 非目标

- 不恢复已撤销订阅的使用权。
- 不为补偿天数新增重置次数或创建新的购买周期。
- 不推断无法由本地交付、上游订阅历史或补偿记录支持的外部延期来源。
- 不修改 Sub2API 的订阅、延期或撤销语义。
- 不允许普通用户选择、覆盖或迁移周期绑定。

## 核心规则

### 订阅代际

同一用户和分组可以先后存在多个上游订阅。每个不同的 `subscription_id` 是一个独立订阅代际。

本地周期一旦绑定到某个代际，普通对账不得将其迁移到另一个 `subscription_id`。只有管理员针对歧义记录做显式决议时才能建立原先不存在的绑定；已建立绑定的冲突修改必须拒绝并记录诊断。

### 补偿延期

一次成功补偿只把已绑定周期的 `period_end` 延长相同天数。原有 `reset_limit`、`reset_used` 和周期开始时间保持不变。

例如 30 天、3 次重置的购买周期补偿 4 天后，3 次机会在完整 34 天内有效。补偿不会产生新的 3 次机会。

上游跨度中无法由本地购买和已知补偿解释的部分仍视为外部区间，不自动获得重置权益。

### 历史失效订阅

绑定到 `revoked` 或已经结束的上游订阅代际后，历史周期标记为已处理且不授予旧数据重置次数。此结果必须参与补发任务的 `processed_records`，防止任务永久重试。

当前有效或未来排期中的购买周期才可以获得补发次数。

## 数据模型

### `subscription_extension_events`

新增延期事件账本：

- `id`
- `event_key`：全局唯一幂等键
- `source_type`：`compensation`、`legacy_compensation` 或 `manual_resolution`
- `compensation_batch_id`、`compensation_detail_id`：可空来源引用
- `upstream_user_id`
- `sub2api_group_id`
- `upstream_subscription_id`
- `extension_days`
- `before_expires_at`
- `after_expires_at`
- `status`：`reserved`、`succeeded`、`failed`、`uncertain`
- `error_message`
- `resolution`：空、`applied` 或 `released`
- `applied_period_id`、`applied_at`
- `reserved_at`、`completed_at`、`confirmed_at`、`confirmed_by_user_id`
- `inferred_from_legacy`、`migration_version`
- `created_at`、`updated_at`

约束：

- `event_key` 唯一。
- 同一补偿明细和上游订阅最多一条事件。
- `extension_days > 0`。
- 新产生的 `compensation` 事件在 `succeeded` 时必须具有延期前后时间，且 `after_expires_at > before_expires_at`。
- `legacy_compensation` 事件允许延期前后时间为空，但必须保存来源明细、确定的延期天数、`inferred_from_legacy = 1` 和迁移版本；它不能作为未知上游操作的自动确认依据。
- 同一事件只能原子应用到一个本地周期一次。

### 周期绑定字段

为 `subscription_reset_periods` 增加：

- `binding_status`：`unbound`、`bound`、`ambiguous`、`ineligible`
- `binding_source`：`delivery_snapshot`、`exact_start_match`、`ordered_extension_match`、`manual_resolution`
- `binding_version`
- `binding_diagnostic`
- `bound_at`

已有 `upstream_subscription_id` 继续保存冻结后的代际绑定。`ineligible` 表示已唯一绑定，但上游订阅已撤销或已过期，因此不授予补发次数。

### 修复任务

新增：

- `subscription_reset_repair_runs`
- `subscription_reset_repair_items`

修复任务保存版本、模式、状态、输入快照摘要、统计、错误和操作人。每个 item 保存本地周期、候选订阅快照、已知补偿事件、建议决议、实际决议以及应用前后状态。

`dry-run` 可以写入修复任务和 item 以保留审计证据，但不能修改周期、次数或原补发任务。`apply` 只能应用同一 run 中仍与当前数据版本一致的确定性 item；数据发生变化时必须拒绝并要求重新 dry-run。

## 上游客户端

扩展 Sub2API 客户端，支持按用户读取所有订阅状态，而不只读取 `active`：

- 分页读取全部订阅。
- 保留 `active`、`revoked` 和其他终止状态。
- 校验分页元数据、用户归属、分组、订阅 ID、开始和到期时间。
- 读取失败不能改变已确认的本地绑定。

所有请求继续只使用后端管理员 API Key，错误日志必须脱敏。

## 代际匹配算法

### 新交付

新交付继续优先使用充值前后上游响应确定 `subscription_id` 和边界。成功交付时立即冻结绑定，后续不依赖历史推断。

### 历史交付

历史未绑定周期按用户和分组读取全部上游订阅，然后按以下证据优先级匹配：

1. 已保存的交付快照或已有 `upstream_subscription_id`。
2. 本地 `fulfilled_at` 与上游 `starts_at` 或 `created_at` 在 5 分钟容差内的唯一匹配。
3. 在同一订阅代际内，按 `fulfilled_at`、`access_request_id` 顺序能够形成不重叠连续购买区间的唯一匹配。
4. 其他情况标记为 `ambiguous`。

匹配时必须同时满足用户、分组和交付时间证据。不能因为某个订阅当前为 active 就把同组全部历史周期绑定到它。

每个订阅代际独立计算：

- 购买周期先按档位 `validity_days` 建立。
- 已确认延期事件按发生顺序延长该代际最后一个有效本地周期。
- 无法解释的上游额外跨度作为外部区间保留。
- 一个代际失败或歧义不能阻塞其他代际。

绑定后根据上游状态决定补发：

- 当前有效且周期覆盖当前时间：授予冻结的 `reset_limit`。
- 未来排期：保留冻结次数，开始后可用。
- 已撤销或已结束：标记 `ineligible`，处理完成但不授予。

## 补偿事务

批量补偿对每个订阅独立执行：

1. 权威读取延期前订阅状态。
2. 写入 `reserved` 延期事件，保存旧到期时间和幂等键。
3. 提交本地预留。
4. 使用同一幂等键调用上游延期接口。
5. 成功时校验返回订阅 ID 和新到期时间，在一个本地事务中把事件标记为 `succeeded` 并应用到已绑定周期。
6. 明确失败标记为 `failed`，不改变周期。
7. 超时、连接中断或响应不可验证时标记为 `uncertain`，不得自动再次延期。

若成功事件发生时尚无已绑定周期，事件保持未应用状态；周期后续完成绑定时再幂等应用。

`uncertain` 事件只有在当前上游到期时间精确等于操作前到期时间加延期天数，并且不存在时间上重叠的其他本地延期事件或已知外部修改时，才能自动确认成功。只要存在其他可能解释该变化的延期，事件就继续保持 `uncertain`。无法唯一证明时由管理员选择 `applied` 或 `released`，且不再次调用上游。

补偿批次结束后非阻塞唤醒订阅重置对账循环。

## 历史补偿迁移

已有补偿明细保存了批次、用户、订阅 ID、延期天数和成功状态，但没有保存延期前后到期时间。

迁移按补偿发生顺序为成功的订阅延期生成 `legacy_compensation` 事件：

- 用户 5、6、16 分别生成 `+3 天`、`+1 天`事件。
- 事件的 `extension_days` 和来源引用被冻结。
- 不使用当前总到期时间虚构操作前边界。
- 绑定周期建立后，按确定的延期天数累计延长 `period_end`。
- 当前上游跨度中超出购买有效期和已知补偿总天数的部分继续视为外部区间。

历史事件的推断来源和迁移版本必须保留，重复迁移不得生成重复事件。

## 管理员接口与界面

新增管理员接口：

- 创建修复 dry-run。
- 查询修复 run 和 item。
- 应用已确认的 dry-run。
- 查询 `ambiguous` 周期及候选订阅。
- 对单个歧义 item 执行 `bind_and_grant`、`bind_without_grant` 或 `keep_pending`。
- 查询和处置 `uncertain` 延期事件。

管理员界面展示：

- 本地申请、交付时间、档位和周期。
- 候选上游订阅的 ID、状态、开始和到期时间。
- 已知补偿事件和累计补偿天数。
- 自动建议及其证据。
- 应用前后的周期边界和重置次数。

人工决议必须二次确认、记录操作人，并保证相同决议幂等、冲突决议返回 `409`。

## 生产数据修复预期

版本 2 修复任务对当前生产数据应产生以下确定性结果：

- 用户 5、订阅 17：绑定原购买周期，叠加 `+4 天`已知补偿，保留已经获得的 3 次权益。
- 用户 6、订阅 15：同上。
- 用户 1、申请 14、订阅 18：精确开始时间匹配；订阅已撤销，标记已处理但不授予。
- 用户 1、申请 22、订阅 21：精确开始时间匹配；绑定当前有效周期并授予 3 次。
- Std 补发任务重算为 `total_records=4`、`processed_records=4`、`granted_records=3`，状态为 `succeeded`。
- Pro 两条周期对应的订阅均已撤销，保持处理完成且零授予。
- Plus 没有历史本地周期，保持零记录。

修复任务必须从周期真实状态重算补发统计，不能直接写死上述计数。

## 上线与回滚

1. 备份生产 SQLite 主文件、WAL 和 SHM，确认可恢复。
2. 部署数据库结构、延期事件写入和新代际对账算法。
3. 迁移后的历史未绑定周期设置为 `binding_status = unbound`、`binding_version = 1`，普通后台对账不得抢先改变这些记录；只有版本 2 repair apply 或管理员决议可以升级其绑定版本。
4. 运行 dry-run 并导出完整 item 列表。
5. 核对结果与“生产数据修复预期”一致。
6. 执行 apply。
7. 验证用户 1 的 Std 卡片已绑定当前周期且显示 3 次机会。
8. 验证 Std 补发任务停止失败重试。
9. 观察至少两个完整对账周期，确认边界、次数和状态不漂移。

回滚时先停止新版本服务，再恢复数据库备份和旧程序。不得只回滚程序而保留新版本已经修改的周期数据。

## 测试

数据库测试覆盖：

- 重复迁移。
- 延期事件唯一约束和状态约束。
- 历史补偿事件幂等生成。
- dry-run 不修改权益数据。
- apply 数据版本校验和重复执行。

服务测试覆盖：

- 同一用户和分组存在多个 active、revoked、expired 订阅代际。
- 精确开始时间匹配。
- 同代际多个连续购买周期。
- 无法唯一匹配时只标记当前 item 为 `ambiguous`。
- 撤销周期处理完成但不授予。
- 补偿延长周期但不增加次数。
- 上游延期成功、明确失败、结果未知和崩溃恢复。
- 延期事件先于周期绑定和后续补应用。
- 当前生产数据的完整回归场景。

HTTP 和前端测试覆盖：

- dry-run、apply 和人工决议权限。
- 幂等重放和冲突决议。
- 候选订阅、补偿证据和应用前后差异展示。
- 移动端对话框滚动和操作按钮可达。

最终运行后端全量测试、前端测试和构建，并在生产备份副本上运行一次 dry-run 集成验证。

## 验收标准

- 当前有效购买周期不会被同组已撤销历史订阅阻塞。
- 补偿后重置次数不增加，但有效期随已确认补偿延长。
- 已撤销和过期周期不会获得补发，也不会导致任务永久失败。
- 歧义记录可见、可审计且不影响其他周期。
- 修复任务 dry-run 与 apply 结果一致，重复执行不重复授权。
- 生产 Std 补发任务达到 `4/4` 已处理、`3` 条已授予，用户 1 当前 Std 卡片恢复正确权益。
