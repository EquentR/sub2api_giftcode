## Task TASK-AUX-001: 隔离并展示旧版规则迁移状态

### Goal

以兼容扩展方式引入模型集合、有序泳道和运行状态所需的持久化能力，并把旧版主力/备用规则安全转换为待迁移的双泳道规则。升级后不得猜测模型集合，也不得因周期检查或手动检查改变旧规则的上游 `schedulable` 状态；管理员仍能通过管理界面看到规则、迁移要求和实际观测状态。

### Acceptance

- 从旧版数据库升级时，原主力账号按原顺序成为泳道 1，原备用账号按原顺序成为泳道 2，规则 ID、名称、启用标志和审计时间保持不变。
- 迁移后的旧规则模型集合为空并明确标记为“需要迁移”；旧 `idle`/`backup_active` 仅作为迁移来源信息保存，不授权任何上游写入。
- 对需要迁移的规则执行周期协调或手动检查时，可以读取并展示上游账号实际状态，但不会发出任何 `schedulable` 写请求。
- 管理列表和前端能够区分“需要迁移”“已禁用”和“正在执行”，不会把待迁移规则描述为受到主动调度。
- 数据库迁移可重复执行，重复启动不会重复转换、丢失成员或改变状态。
- 上游账号信息读取失败时，已持久化规则仍然可见，并显示可操作的上游错误。

### Dependencies

- None

### Test seam

- 通过完整管理员路由验证认证、响应封装和迁移状态；通过既有轻量前端测试验证迁移提示和观测状态展示。

## Task TASK-AUX-002: 交付新泳道规则配置与排他所有权

### Goal

让管理员能够端到端创建、编辑、查看和启用模型集合泳道规则，并通过持久化所有权关系保证启用规则之间的账号排他性。配置保存只改变本地策略和期望状态，不在 CRUD 请求内直接执行上游切换。

### Acceptance

- 新规则要求非空模型集合、至少两个按成本排序且非空的泳道，以及位于有效范围内的 `maximum_auto_lane`。
- 同一账号不能在一条规则的多个泳道中重复出现；配置模型必须能根据账号支持模型及映射进行一致验证。
- 只有已启用且不再需要迁移的规则占有账号；已禁用或待迁移规则不占有账号，其账号可被其他规则使用。
- 启用规则之间的账号冲突由持久化存储事务性拒绝，失败时配置和所有权均不发生部分变化。
- 管理界面提供模型多选、有序泳道编辑、泳道增删和排序、自动泳道上限，并明确提示累积开放不等于严格成本隔离。
- 保存待迁移规则时，只有管理员显式选择模型并形成有效配置后才能清除迁移状态；保存请求本身不发出 `schedulable` 写入。
- 新契约能够通过已认证的管理 CRUD 完整往返，上游补充信息失败不隐藏本地规则。

## Task TASK-AUX-003: 以权威回读协调静态期望前缀

### Goal

建立后续自动升级所依赖的财务安全执行器：先持久化期望开启前缀，再将每个账号的 `schedulable` 状态向期望值收敛；每次写入必须通过权威账号读取验证。部分成功、超时和进程重启后都能继续收敛，任何未解决的不确定状态都会阻止开启更多泳道。

### Acceptance

- 启用有效规则后，系统先持久化期望前缀，再通过周期或手动协调执行上游变更；CRUD 保存路径不另建一套切换逻辑。
- 期望开启状态始终是从泳道 1 到目标泳道的连续前缀；开启按低成本到高成本执行，关闭按高成本到低成本执行。
- 每次 `schedulable` 写入后必须读取同一账号，核对账号 ID 和最终开关值；仅收到成功 HTTP 响应不算验证成功。
- 响应数据缺失、账号身份不符、回读失败、最终值不符或请求超时会产生可见的 `uncertain` 或 `failed` 状态，而不是稳定状态。
- 存在未解决的不确定变更时，不得开启额外泳道。
- 每次协调都会读取权威状态并修复人工漂移；漂移被纠正并产生管理员可见警告。
- 在部分写入后重建应用服务实例，系统能依据持久化期望状态继续收敛，不会发明新的目标前缀。
- 手动检查与周期调度使用同一协调行为路径并产生相同结果。

## Task TASK-AUX-004: 根据模型集合联合覆盖逐级升级

### Goal

在已验证执行器之上实现类型化模型可用性观测和累积升级策略。调度器根据当前已开启前缀内所有账号的联合模型覆盖决定是否只开启下一泳道，并在状态未知或超过自动上限时拒绝授权额外支出。

### Acceptance

- 可用性观测对每个账号与目标模型返回 `usable`、`unavailable` 或 `unknown`，并考虑账号状态、账号级临时时间窗、模型级冷却、支持模型、模型映射和数据有效性。
- 面向请求的模型名称与账号映射及 `model_rate_limits` 键采用一致解析；格式异常、缺失或无法权威读取的数据判定为 `unknown`，不会判定为可升级证据。
- 当前前缀的覆盖按所有已开启泳道的账号并集计算；不同账号可以互补覆盖模型集合。
- 确定性账号整体失效可以立即确认覆盖缺口；临时模型级缺口需要连续两次协调观测。
- 一次协调最多将期望前缀扩展一个泳道，并保留所有更便宜泳道开启。
- 下一泳道超过 `maximum_auto_lane` 时不执行开启，规则显示独立的自动上限阻塞状态和缺失模型。
- 任一授权升级所需的观测为 `unknown` 时不升级，并保留最近一次已验证的期望状态。
- 升级原因、缺失模型、确认证据和当前期望/已验证前缀可通过管理接口观察。

## Task TASK-AUX-005: 稳定恢复到最低充分前缀

### Goal

在低成本容量恢复后，找出能够完整覆盖模型集合的最低成本前缀；只有同一候选前缀连续稳定约两分钟后，才从最高成本泳道开始收缩，并通过已验证执行器安全关闭多余容量。

### Acceptance

- 每次协调都会计算当前能够完整覆盖模型集合的最低成本前缀，并持久化恢复候选及开始时间。
- 候选前缀变化、覆盖再次缺失或观测变为未知时，原稳定计时失效并按规范重新开始或暂停。
- 稳定期未满约两分钟时，不改变期望开启前缀，也不发送关闭请求。
- 稳定期满足后，期望前缀收缩到最低充分前缀；多余泳道按成本从高到低关闭，保留前缀内账号开启。
- 关闭结果未验证或不确定时，运行状态保持非稳定，并在后续协调中继续收敛。
- 恢复候选、稳定进度、目标前缀和关闭结果能够通过管理接口观察。
- 所有时间测试使用可控时钟，不依赖真实等待或调度器 ticker。

## Task TASK-AUX-006: 安全处理禁用、删除和成员变更

### Goal

让规则生命周期操作复用已验证的期望状态协调协议。禁用、删除或修改已启用规则时，必须先安全处理不再受控的高成本账号，再事务性释放所有权或应用新配置；无法验证清理结果时，不得声称操作完成。

### Acceptance

- 禁用或删除规则时，泳道 1 账号保持 `schedulable`，泳道 1 以上账号从最高泳道开始关闭并完成权威验证后，才释放所有权或删除规则。
- 更新已启用规则时，被移除的非基准账号必须先关闭并验证；被移除的泳道 1 账号保持开启后释放。
- 泳道重排和成员替换不会产生无所有权的已开启高成本账号，也不会在清理完成前允许其他规则认领相关账号。
- 清理失败或结果不确定时，原规则、原所有权和可恢复转换状态得到保留，操作不会被报告为已完全应用。
- 后续重试能从持久化状态继续清理；清理成功后账号可以被另一条启用规则事务性认领。
- 禁用、删除和更新通过管理接口返回可理解的稳定、失败或不确定结果，前端不会提前移除仍在清理的规则。
- 生命周期操作不会创建独立于周期/手动协调之外的未验证上游写入协议。

## Task TASK-AUX-007: 完成运行态管理界面与公共契约

### Goal

完成管理员对新调度策略的运行态观察和操作体验，并将管理契约统一到模型集合、有序泳道和前缀状态。所有对外可区分状态都必须可通过接口表达并在界面正确呈现，同时持久化规则不能因上游补充信息失败而消失。

### Acceptance

- 管理列表和手动检查响应公开期望、观测和已验证前缀，以及缺失模型、升级原因/证据、恢复进度、转换代次、警告和阻塞原因。

## Task TASK-AUX-008: 收缩旧契约并完成全量验收

### Goal

在所有新流程可用后移除运行时对旧主力/备用公共契约的依赖，完成迁移、协调、生命周期和管理界面的累积回归验证，并更新运维文档。旧数据库字段只作为仍待迁移记录的内部来源保留，不在本任务中执行有风险的物理删除。

### Acceptance

- 管理创建、更新、列表和手动检查仅使用模型集合与有序泳道公共契约；旧形状写请求被明确拒绝，不会被静默猜测或转换。
